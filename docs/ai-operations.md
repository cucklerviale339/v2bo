# AI 运维

本模块参考 `jiasu9527/v2b-private` 的 `f64b67179f197b9cd549de5f94b5c7a8e8feaa33`，适配到当前 Forest 的用户、节点、地址规则、备用监控和鉴权接口。后台入口为“AI 运维”（`/<后台路径>/config/ai-ops`）。首次安装默认关闭，没有预置 API Key。

## 工作方式

管理员选择模型并发送问题后，后端建立持久会话，调用兼容 OpenAI Chat Completions 的接口，通过 SSE 向页面更新回答、工具调用和操作结果。模型通过固定工具及后台操作目录访问业务，不能自行指定后台 URL 或 SQL。大查询结果按会话暂存，可继续分页读取。会话支持停止、历史查询和请求去重。

可查询用户、订单、套餐、工单、节点、入口监控和备用 IP；可通过受控操作修改相应配置。支付配置不向模型开放。支持登记 SSH 服务器、读取并固定主机指纹、执行受控 SSH 命令、查看执行结果；凭据通过加密表单或专用登记流程保存。知识库支持共享、草稿/生效状态及版本校验。模型中转支持主服务和最多四个备用服务，以及超时切换和故障冷却。

访问模式沿用参考项目：新会话默认“完全访问”，模型提出的获准写操作会自动执行；切换为“逐次确认”后，写操作先生成待审记录，批准才会执行。审批会检查会话、权限、过期和目标快照，已执行的操作不能再次审批。写操作结果未知时只允许后续只读核对，不自动重放写入。使用者应按需要选择访问模式。

管理员可配置模型和管理会话；员工仅能访问本人会话，并受各专用工具的权限限制。通过通用目录委托现有后台接口的操作仅向管理员开放，因为本项目原有员工接口不具备参考项目的全部事务权限保护。后端每次重新验证角色。Web 页面另调用 `/ai-ops/identity` 获取真实操作人 ID/角色，避免依赖不含角色的普通用户信息接口。

## 本项目的入口适配

入口状态直接读取本项目 `ListDispatchMonitors`；备用 IP 读取 `ListDispatchPool`，复用现有探针结果。下发地址优先级仍是内鬼规则、绑定的节点地址规则、节点原地址。仅纳入已启用且实际链路会下发的节点入口，按地址去重并显示对应 ID/范围及来源。关闭的地址规则不生效，按实际链路回退。账号可用状态、节点权限和其他匹配谓词仍按当前入口清单的既有约定处理。

额外节点/额外订阅不纳入入口清单。AI 读取地址与内鬼规则时隐藏额外订阅链接；修改普通字段时后端保留原链接和位置设置，AI schema 不接受改写 `extra_nodes`。本次没有引入参考项目的入口自动拆分和主动检测机制。检测端口只影响探针，原订阅端口不因此变化。已有探针并发和调度保持原实现。

## 配置

1. 在“设置”填写中转地址、API Key 和该服务真实可用的模型名称，再开启 AI。模型下拉框中的初始名称沿用参考项目，是否可用取决于所配置服务，应替换成自己的服务支持的名称。
2. 可配置备用中转及超时时间。各服务的模型和 Key 分别配置。
3. SSH 服务器登记时核验主机指纹，并填写所需凭据。完全访问模式下 SSH 写命令也可能自动执行。
4. 通过知识页保存适合长期使用的运维规则。不要把密码、Token 或私钥保存到共享知识。

`APP_KEY` 必须长期保持不变。模型 Key、SSH 密码和私钥等使用派生自 `APP_KEY` 的 AES-GCM 密钥加密；接口只返回已配置状态，不能读取明文。数据库备份必须与原 `APP_KEY` 配套保存，更换它会使已有密文无法解密。会话和工具结果仍可能包含业务信息，按运维数据管理。

## Telegram

后台 Telegram 页提供独立的运维账号绑定、配置与 Mini App 入口。Mini App 校验 Telegram 签名和有效期，使用独立的短期运维 Token；该 Token 不能用于普通后台或用户接口，浏览器普通登录凭据也不被 Mini App 使用。页面的 Mini Token 只保存在内存。

AI 运维更新要求 Telegram Webhook 的 secret header。已有 Bot 升级后，应使用当前后台重新保存 Bot/Webhook 配置，让 `setWebhook` 携带由 `APP_KEY` 与 Bot Token 派生的 `secret_token`；完成独立运维绑定后才能使用。真实 Telegram 收发及 Mini App 还需要可用 Bot、公开 HTTPS 入口和 Telegram 客户端。无这些配置时仅能验证本地鉴权与路由边界，不能视为已验证实际收发。

## 升级、验证和回退

AI 表以 `v2_ai_` 为前缀，首次访问按需创建，使用事务锁并可重复初始化；不会迁移或重写原用户、节点和地址业务记录。升级前备份数据库、原二进制、前端资源、配置及 `.env.go`。同步更新后端与编译后的前端，重启对应实例。

验证包括 Go 全套回归、隔离 PostgreSQL schema 的升级/业务流程、流式模型工具调用、权限隔离、操作审批、知识版本、SSH 及前端脚本和浏览器验收。模型兼容性与实际回答质量需使用真实服务另外验证。既有生产版本的迁移检查不能替代真实生产数据备份。

回退时先关闭 AI，恢复原二进制和前端资源，保留 `APP_KEY`；新增 AI 表可以保留。不要直接导入旧数据库覆盖已发生的新业务数据；如确需数据库恢复，先停止写入并确认恢复时间点。AI 历史、服务器凭据等清理使用后台提供的明确确认操作。
